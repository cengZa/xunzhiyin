# Reference Sample Gap Review

本页记录当前论文与 `docs/更多参考/本科论文-工程型样例-刘.docx` 的主要差异，后续按导师要求继续收敛。

## 1. 第 4 章内容组织差异

- 范文第 4 章按“系统体系结构、系统功能结构、数据库设计”组织，数据库设计中在 ER 图后连续给出表结构详细设计。
- 当前论文第 4 章已调整为“系统架构设计、系统功能结构、数据库设计、Redis 设计、本章小结”。其中 Redis 设计是本系统推荐召回和画像缓存的核心支撑，因此保留为独立小节。
- 范文在第 4 章前半部分不使用“系统分层结构说明表、核心模块职责表”这类说明型表格；当前论文已删除第 4 章前半部分说明型表格，将表 4-1 至表 4-7 改为数据库物理表结构设计。

## 2. 图 4-1 差异

- 范文图 4-1 是黑白线框体系结构图，左侧展示外部系统，中央展示系统边界、前端、服务端模块、数据存储和数据处理，右侧展示平台服务。
- 当前论文图 4-1 已改为同类黑白线框风格：左侧展示校园用户、系统管理员、前端页面和测试/演示入口，中央展示校园社交匹配推荐系统边界、前端展示层、服务端模块、MySQL 和 Redis，右侧展示外部大语言模型服务与后续扩展服务。
- 保留差异：范文业务域包含 Kafka、Flink、RPC 微服务和企业内部平台；当前系统采用 Spring Boot 单体分层架构，不引入 Kafka/Flink，外部服务只保留大语言模型解释改写入口。这是项目技术方案差异，不应为了贴近范文而虚构组件。

## 3. 表 4-1 模板差异

- 范文表 4-1 形式为“表题 -> 表名：xxx -> 序号/字段名/类型/属性/描述”。
- 当前论文已按该模板补充表 4-1 至表 4-7，覆盖 `user`、`tag`、`user_tag_relation`、`user_profile`、`recommendation_result`、`recommendation_explanation`、`user_feedback`。
- 当前表 4-1 至表 4-7 已由 Word 组稿器生成原生 Word 表格，表头浅蓝底色、黑色边框和字段清单列均按范文表 4-1 靠拢。
- 当前 Word 组稿器已将全文 Markdown 表格统一生成为原生 Word 表格，第 6 章测试用例表按范文表 6-2 的四列用例模板处理，并对长文本说明行进行单元格合并。

## 4. 第 5 章界面图差异

- 范文第 5 章使用系统运行效果截图，展示真实页面、筛选条件和列表内容。
- 当前第 5 章界面图已替换为本地运行系统后截取的真实浏览器截图，不再使用占位符。
- 图 5-4 展示首页推荐结果，图 5-8 展示透明链路最终 Top-K，图 5-12 展示解释对照区域，已基本贴近范文中“实现效果图”的呈现方式。

## 5. 字体和版式差异

- 正文 Word 仍基于学校论文主体模板，页眉、正文、标题和页码规则与模板保持一致；范文同样使用北京交通大学论文模板。
- 图表图片内部文字由脚本生成，当前 macOS 下优先使用宋体，标题等加粗位置使用黑体类字体；与范文中由 Word/WPS 图形对象渲染出的字体仍可能存在细微字重差异。
- 正文表格已改为 Word 原生表格，可编辑且可随 Word 版式自然重排。
- 当前论文图题、表题位置与范文一致：图题在图下，表题在表上。

## 6. 技术框架差异

- 范文采用微服务、RPC、Kafka、Flink、MySQL、Redis、平台服务等工程架构。
- 当前系统采用 Java 21、Spring Boot、MyBatis-Plus、MySQL、Redis、H2 独立验证和少量外部大语言模型服务。该差异由课题规模和推荐系统主链路决定，应在论文中保持真实，不建议照搬范文技术栈。

## 7. 仍需人工确认

- 封面个人信息、致谢内容是否需要个性化修改。
- Word 内自动目录是否需要在最终打开 Word 后手动更新。
- 参考文献是否需要进一步按 GB/T 7714 细节人工校对。
- 若导师要求最终目录页码完全动态，需要在 Word/WPS 中打开终稿后更新目录域或确认静态目录页码。

## 8. 开发型论文范文可借鉴点

本节对照 `docs/更多参考/开发型论文 范文.pdf`，记录当前论文后续可吸收的组织和图表表达方式。

### 8.1 摘要写法

- 范文摘要结构清晰：先写项目背景和痛点，再按三个主要模块逐项说明，随后给出关键算法或技术的量化结果，最后说明系统应用效果。
- 当前论文摘要已调整为“背景 -> 系统核心功能 -> 测试结果”的工程型结构，删除“本人独立完成”表述，并把透明链路展示、双视图对比和评估导出并入“推荐解释与用户反馈模块”，使摘要、目录和正文三大模块保持一致。
- 范文的结果段有明确数值和应用状态，例如准确率提升、接入对象数量、运行状态。当前论文已有 18 个用户、36 个标签、130 条关系、解释覆盖率 1.0000 等结果，可继续保留，但不应虚构线上部署效果。

### 8.2 目录与章节组织

- 范文采用“引言 -> 关键技术 -> 需求分析 -> 概要设计 -> 算法设计 -> 详细设计 -> 测试 -> 总结”的开发型结构。
- 当前论文采用“引言 -> 相关理论 -> 需求分析 -> 概要设计 -> 详细设计与实现 -> 测试 -> 总结”。该结构更适合当前推荐系统，因为算法设计规模不足以单独成章。
- 可借鉴的是范文第 4 章的概要设计顺序：系统整体架构设计、系统功能模块设计、系统核心流程设计、数据存储设计。当前第 4 章缺少“系统核心流程设计”小节，建议补充。

### 8.3 第 4 章概要设计图

- 范文图 4-1 使用五层架构表达：访问层、应用层、支撑层、数据层、设施层。当前图 4-1 已有分层结构，但图题可改为“图 4-1 系统整体架构图”，并进一步突出访问层、业务层、数据层、外部服务层。
- 范文图 4-2 是树形功能模块结构图，模块和子功能层级清楚。当前图 4-2 已有功能结构，但可以改名为“系统功能模块结构图”，并用树形结构表达三个主体模块及其子功能，避免与架构图风格过近。
- 范文图 4-3 是系统核心流程图，用一张流程图串起用户登录后的主要路径。当前论文缺少同级别的核心流程图，建议新增“图 4-3 系统核心流程图”，内容可按“用户登录 -> 标签维护/画像构建 -> 推荐生成 -> 推荐解释 -> 用户反馈 -> 画像更新 -> 结果复核”绘制。

### 8.4 数据存储模型

- 范文把数据存储设计拆成概念模型、逻辑模型、物理模型三层，并分别配图 4-4、图 4-5、图 4-6，再给出物理表结构。
- 当前论文按本次要求不再分别绘制概念模型和逻辑模型，而是用一张 Peter Chen 表示法 ER 图展示实体、关系和关键属性，再用物理模型图和表 4-1 至表 4-7 展示 MySQL 落表结构。
- 该差异属于主动调整：范文三层模型适合较大企业系统，当前系统实体较少，拆分概念图和逻辑图会造成内容重复，因此采用“ER 图 + 物理模型 + 表结构”的表达更紧凑。

### 8.5 详细设计章的模块展开方式

- 范文第 6 章每个核心模块一般按“业务流程图 -> 子功能类图 -> 时序图 -> 实现效果图”的顺序展开。
- 当前第 5 章已补充为“业务流程图 -> 类图 -> 时序图 -> 实现效果图”的展开方式，并分别增加用户画像构建、匹配推荐生成、推荐解释与用户反馈三个模块的业务流程图。
- 当前类图已按范文特点突出 Controller、ServiceImpl、Mapper、Repository、策略类和外部服务客户端等元素，但没有为了贴近范文而虚构 VO/DTO 或日志实体。

### 8.6 测试用例表达

- 范文测试章按具体功能给出测试用例，并在用例后描述实际界面表现。
- 当前第 6 章已有功能性与非功能性测试表，组织方式基本可用。可以借鉴范文做法，在每个重要测试表后增加一两句“测试结果说明”，说明该测试回到哪个页面、接口或导出材料。

### 8.7 不建议照搬的内容

- 不建议单独增加“算法设计章”。当前系统的核心工作是推荐链路工程实现和可解释闭环，算法复杂度不足以支撑独立算法章，强行拆章会造成内容空泛。
- 不建议照搬微服务、Kafka、Flink、PowerDesigner 等技术栈。当前项目真实实现是 Spring Boot、MySQL、Redis 和可选大语言模型解释改写，应保持技术真实性。
- 不建议虚构上线运行效果。范文中有企业项目接入风场的数据，当前论文只能写测试数据集和离线评估结果。
