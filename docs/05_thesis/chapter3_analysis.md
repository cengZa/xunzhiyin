# 第 3 章 校园社交匹配推荐系统需求分析

本章在开题目标和现有系统边界的基础上，对校园社交匹配与可解释推荐系统进行需求分析。系统的推荐对象为校园用户，核心任务是在校园学习、社团和兴趣场景下为用户发现潜在匹配对象。围绕这一目标，系统需要解决用户兴趣表达不充分、推荐链路缺少透明度、推荐结果难以解释以及反馈不能反映到后续推荐等问题。

需求分析从总体需求、用户角色与应用场景、功能需求、非功能需求和数据需求五个方面展开。后续系统设计、实现与测试均以本章需求为基础。

## 3.1 需求分析概述

校园社交匹配具有数据规模相对有限、用户关系依赖场景、推荐理由需要容易理解等特点。如果直接采用复杂深度学习推荐模型，不仅实现成本较高，也不利于解释推荐依据。因此，系统需求应优先围绕结构化推荐链路展开：先根据用户标签构建兴趣画像，再通过倒排索引召回候选用户，随后进行相似度排序、校园规则重排和推荐解释生成，最后通过用户反馈对画像进行轻量更新。

从需求角度看，系统应具备完整的推荐主链路、清晰的数据模型、可追溯的解释机制和可重复的测试材料。主要需求可以概括如下：

1. 建立用户、标签、画像、推荐结果、推荐解释和用户反馈等核心数据模型。
2. 实现从用户标签到 Top-K 推荐结果的完整推荐链路。
3. 在画像阶段引入改进 TF-IDF、时间衰减和 Top-K 裁剪机制，提高用户画像的区分度。
4. 在排序结果基础上引入校园规则重排，使推荐结果更贴合学习搭子、社团搭子和兴趣同频等场景。
5. 保证推荐解释来自标签贡献项和规则命中证据，避免生成脱离推荐过程的解释文本。
6. 提供自动化测试、运行数据和离线评估材料，支撑系统验证和论文分析。

上述需求限定了系统的工程规模。系统优先保证推荐流程可运行、可解释、可验证，不引入复杂分布式推荐架构或深度学习训练平台。

## 3.2 用户角色与场景需求

系统定位为面向校园用户的匹配推荐系统，主要参与者包括普通校园用户、系统管理员和外部大语言模型服务。普通校园用户负责维护个人资料和标签、获取推荐结果、查看推荐解释并提交反馈；系统管理员主要负责标签体系、用户数据和评估材料维护；外部大语言模型服务仅用于解释文本润色，不参与推荐计算。

系统主要服务于以下三类场景：

1. 学习搭子推荐：根据课程、专业、学习兴趣等标签匹配具有相近学习目标的用户。
2. 社团搭子推荐：根据社团、活动和校园经历等标签匹配可能产生线下联系的用户。
3. 兴趣同频推荐：根据兴趣爱好标签发现具有相似偏好的用户，并允许保留轻量探索空间。

在项目范围内，系统重点覆盖用户信息维护、标签维护、画像构建、候选召回、排序重排、解释生成、反馈记录和演示评估能力。

表 3-1 系统功能范围说明

| 模块 | 范围说明 |
| --- | --- |
| 用户管理 | 维护用户基础信息，为推荐链路提供用户上下文 |
| 标签管理 | 维护标签定义、标签分类和用户标签关系 |
| 用户画像 | 基于改进 TF-IDF、时间衰减和 Top-K 机制生成兴趣画像 |
| 候选召回 | 根据 Top-K 标签和倒排索引生成候选用户集合 |
| 排序重排 | 根据相似度和校园场景规则得到最终排序 |
| 推荐解释 | 根据标签贡献和规则命中生成可追溯推荐理由 |
| 用户反馈 | 记录关注、忽略等反馈，并触发画像轻量更新 |
| 运行评估 | 提供校园用户数据集、透明链路、双视图对比和离线评估材料 |

同时，系统不试图覆盖完整社交产品的全部能力。以下内容不属于本项目范围：

1. 即时聊天、好友关系链和消息通知系统。
2. 内容流、发帖、评论、审核和社区治理能力。
3. 大规模在线推荐服务、实时特征平台和在线 A/B 实验平台。
4. 大规模问卷统计和长期反馈收益分析。
5. 深度学习推荐模型训练、向量召回平台和复杂分布式部署。

通过明确角色、场景和范围，系统评价可以集中在推荐主链路、解释机制和工程可验证性上。

## 3.3 功能需求

系统功能需求依据开题阶段的需求分析和后续实现结果整理，并与实现模块、测试材料和论文章节保持对应。功能需求围绕推荐链路分为七类。

### 3.3.1 用户与标签管理需求

系统应支持用户基础信息的创建、查询和维护。用户信息至少应包含昵称、年级、专业、学院、个人简介等字段，以便在推荐重排和解释中使用校园上下文。系统还应支持标签定义、标签分类和用户标签绑定。标签类型需要覆盖学习、兴趣、社团、年级专业等维度，为后续画像生成提供原始数据。

该类需求是推荐链路的数据入口。若用户标签关系缺失，画像计算、倒排召回和推荐解释均无法成立。

### 3.3.2 用户画像生成需求

系统应根据用户标签关系构建用户兴趣画像。画像生成不能只进行简单标签计数，而应综合考虑标签频次、标签区分度、时间衰减和 Top-K 裁剪。通过改进 TF-IDF 权重计算，系统能够降低高频普通标签的影响，突出更能区分用户兴趣的标签。

画像结果既要支持推荐计算，也要为解释生成提供依据。因此，画像数据应保存标签权重向量和 Top-K 核心标签。

### 3.3.3 候选召回需求

系统应根据目标用户画像中的 Top-K 标签召回候选用户。召回阶段采用标签到用户的倒排索引结构，将拥有相同或相近标签的用户快速合并为候选集合。召回结果需要过滤请求用户自身，并为后续排序保留公共标签信息。

候选召回的主要目标是缩小排序计算范围，避免对全部校园用户逐一计算相似度，从而提高推荐链路的执行效率。

### 3.3.4 排序与重排需求

系统应对候选用户进行基础排序和场景重排。基础排序使用余弦相似度计算目标用户画像与候选用户画像之间的兴趣相似度，并记录共同标签贡献项。重排阶段在基础排序结果之上引入校园场景规则，例如年级差、专业相关性和社团重合度。

系统还应支持不同推荐场景模式。学习搭子模式强调学习标签和专业相关性，社团搭子模式强调社团重合和校园活动联系，兴趣同频模式强调兴趣相似度并允许轻量探索位。

排序与重排共同决定最终 Top-K 推荐结果，是系统推荐效果和业务合理性的核心环节。

### 3.3.5 推荐解释需求

系统应为每条推荐结果生成推荐原因。解释必须能够回溯到排序贡献项或重排规则命中，不能脱离推荐证据单独生成。推荐解释至少应说明共同标签、标签贡献和校园规则命中情况，使用户能够理解推荐依据。

系统可以使用 LLM 对规则解释文本进行润色，但 LLM 不能参与召回、排序、重排、可信连接分计算或反馈更新。若外部 LLM 不可用，系统仍应返回基于规则的解释文本。

推荐解释的重点在于保证解释与推荐计算过程一致，而非生成更长的自然语言。

### 3.3.6 反馈采集与画像更新需求

系统应记录用户对推荐对象的反馈行为，包括关注和忽略等类型。反馈记录应与推荐结果关联，使系统能够知道用户针对哪一次推荐产生了何种反馈。在此基础上，系统应根据推荐结果中的主要证据标签对画像权重进行轻量调整，使后续推荐能够体现反馈影响。

反馈更新的评价重点是机制可运行、数据可记录、画像可更新，并使用户行为能够影响后续推荐。

### 3.3.7 推荐记录与运行评估需求

系统应保存推荐结果、推荐解释和用户反馈，便于后续分析、测试和论文展示。为了支持系统复核，系统还应提供数据初始化、透明推荐链路、双视图对比、演示故事线和离线评估摘要导出能力。

该类需求不改变推荐算法本身，但能保证系统具备可复现的展示和验证材料。

## 3.4 非功能需求

除功能需求外，系统还需要满足可实现性、可维护性、可解释性、可验证性、性能可接受和论文一致性等非功能需求。

表 3-2 系统非功能需求说明

| 非功能需求 | 需求说明 | 对系统设计的影响 |
| --- | --- | --- |
| 可实现性 | 系统应适合本科工程项目实现 | 采用 Spring Boot 单体架构，不引入复杂分布式基础设施 |
| 可维护性 | 模块职责应清晰，便于后续扩展 | 按 controller、service、strategy、mapper、domain、infra 分层 |
| 可解释性 | 推荐结果应具备可追溯依据 | 保存标签贡献、规则命中、证据 JSON 和解释文本 |
| 可验证性 | 系统功能和推荐逻辑应可重复验证 | 建立单元测试、集成测试、治理脚本和离线评估快照 |
| 性能可接受 | 小规模校园数据下推荐接口应保持可用响应 | 使用倒排召回减少排序候选集合 |
| 一致性 | 论文、设计、实现和测试应互相支撑 | 建立需求、设计、实现和论文章节的对应关系 |

这些非功能需求决定了系统不能只追求推荐结果输出，还要保证工程结构、解释证据、测试材料和论文表述能够对应。

## 3.5 数据需求

系统需要维护的数据可分为七类：

1. 用户基础信息数据：用于描述推荐请求用户和候选用户的校园属性。
2. 标签定义数据：用于维护学习、兴趣、社团、年级专业等标签类型。
3. 用户标签关系数据：用于记录用户选择或生成的标签，是画像计算和召回的基础。
4. 用户画像数据：用于保存标签权重向量、Top-K 核心标签和画像版本。
5. 推荐结果数据：用于记录一次推荐任务中的候选对象、排序分数、最终名次和追踪标识。
6. 推荐解释数据：用于保存解释文本、证据 JSON 和标签贡献明细。
7. 用户反馈数据：用于记录关注、忽略等反馈行为，并支持后续画像更新。

从数据流角度看，用户标签关系生成画像，画像驱动召回和排序，排序与规则命中生成推荐结果和解释，用户反馈再回到画像更新环节。该数据闭环是系统后续设计与实现的核心依据。

## 3.6 本章小结

本章明确了校园社交匹配与可解释推荐系统的总体需求、用户角色、应用场景、功能需求、非功能需求和数据需求。系统围绕“用户标签 -> 用户画像 -> 候选召回 -> 排序重排 -> 推荐解释 -> 用户反馈 -> 画像更新”形成闭环。后续系统设计与实现章节将围绕该闭环展开，并在测试章节中对主要功能进行验证。
