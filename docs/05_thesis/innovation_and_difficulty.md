# Innovation And Difficulty Notes

本页用于收口论文和答辩中可使用的创新点、重难点与表述边界。写作时应优先强调工程化、可解释、可演示、可验证，不把代理实验写成真实线上效果。

## 1. 可作为论文创新点的内容

### 1.1 面向校园匹配场景的结构化推荐链路

系统不是简单的标签重叠推荐，而是构建了完整链路：

```text
用户画像 -> 候选召回 -> 相似度排序 -> 校园规则重排 -> 可信连接分 -> 解释生成 -> 反馈更新
```

可写价值：
- 推荐对象是校园用户，贴合学习搭子、社团搭子、兴趣同频等场景。
- 链路分层清晰，便于测试、解释和答辩展示。
- 相比单一标签匹配，系统能展示排序前后变化和规则命中原因。

表述边界：
- 不写成大规模线上推荐系统。
- 不宣称达到工业级推荐性能。

### 1.2 改进 TF-IDF 用户画像

系统在用户标签基础上构建兴趣画像，引入：

- TF-IDF 权重
- 标签区分度调节
- 时间衰减
- Top-K 画像裁剪

可写价值：
- 降低热门标签对画像的过度支配。
- 让画像更突出当前用户的代表性兴趣。
- 为倒排召回、排序贡献和解释生成提供统一特征基础。

表述边界：
- 当前缺少“改进前 vs 改进后权重提升 30%”的正式专项实验表，不能直接写成开题量化目标已完全达成。

### 1.3 校园场景化重排

系统在相似度排序之后叠加校园业务规则，包括：

- 年级差
- 专业相关性
- 社团重合度
- 场景模式权重

系统支持三类场景：

| 场景 | 重点 |
| --- | --- |
| `study_partner` | 学习目标、专业相关和稳定连接 |
| `club_partner` | 社团重合和校园活动关系 |
| `interest_partner` | 兴趣同频和潜在连接 |

可写价值：
- 让推荐结果从“相似的人”进一步变成“当前校园场景下更适合连接的人”。
- 便于答辩展示不同场景下推荐顺序变化。

表述边界：
- 当前场景效果主要通过模拟校园用户数据和代理规则验证，不能写成真实用户偏好实验结论。

### 1.4 可信连接分

系统引入轻量可信连接分，用于补充判断候选对象是否具有足够推荐证据。推荐结果返回：

- `trustScore`
- `trustReasons`
- `recommendationLabel`

可写价值：
- 抑制资料稀疏或证据较弱的候选对象仅凭热门标签排到前列。
- 提升推荐结果的可解释性和答辩展示质量。
- 让推荐分数从单一兴趣相似度扩展为兴趣、校园规则和可信连接的组合。

表述边界：
- 可信连接分是轻量规则评分，不是复杂信任网络模型。

### 1.5 推荐解释与证据绑定

系统解释来自排序贡献项和重排规则命中，保留：

- 共同标签
- 标签贡献
- 规则命中
- 证据 JSON
- 规则解释文本

可写价值：
- 避免推荐理由脱离实际排序依据。
- 支持“为什么推荐”和“为什么排在前面”的双层说明。
- 支撑论文中可解释推荐章节和答辩现场追问。

表述边界：
- LLM 解释改写不是核心推荐算法。
- LLM 只润色文本，不改变证据项。

### 1.6 LLM 解释改写与规则回退

系统接入智谱 `GLM-4.7` 作为解释改写能力，同时保留规则回退：

- 有效返回时：`reasonSource=llm`
- 缺少 key、请求失败或超时时：`reasonSource=rule`

可写价值：
- 在不改变推荐结果的前提下提升解释可读性。
- 外部服务不可用时仍能返回稳定解释。
- 体现工程可靠性和可控 AI 使用边界。

表述边界：
- 不写成“使用大模型进行推荐排序”。
- 不写成“LLM 提升推荐准确率”。

### 1.7 轻量探索机制

系统在 `interest_partner` 场景下支持轻量探索：

- 仅在 `topK >= 3` 时启用
- 保持前 2 名主结果稳定
- 最多保留 1 个探索位
- 返回 `explorationReason`

可写价值：
- 在稳定推荐之外保留潜在兴趣连接。
- 适合校园兴趣拓展场景。
- 答辩时可展示“主排序稳定 + 轻量探索”的平衡。

表述边界：
- 当前探索位权重和阈值尚未经过大规模实验优化。

### 1.8 透明链路演示

系统提供 `/pipeline.html` 和聚合接口，展示：

- 输入标签
- 画像权重
- 召回轨迹
- 排序公式
- 重排规则
- 可信连接分
- 探索位
- 最终解释

可写价值：
- 推荐过程可视化，适合本科毕设答辩。
- 降低评委理解系统内部链路的成本。
- 体现系统不仅能给结果，还能说明过程。

表述边界：
- 透明链路是演示与调试能力，不是面向真实用户的完整产品后台。

## 2. 项目重难点

### 2.1 推荐链路一致性

难点：
- 画像、召回、排序、重排、解释、反馈之间容易出现证据断裂。
- 若解释独立生成，容易与排序依据不一致。

解决：
- 排序阶段记录标签贡献。
- 重排阶段记录规则命中。
- 解释阶段只从贡献和规则中抽取证据。
- 推荐详情接口返回证据字段，供页面和测试使用。

### 2.2 热门标签与画像区分度

难点：
- 校园场景中热门标签容易让大量用户看起来相似。
- 单纯标签重叠会导致推荐结果同质化。

解决：
- 使用改进 TF-IDF 和时间衰减。
- 通过 Top-K 标签裁剪保留核心兴趣。
- 在排序后引入场景规则和可信连接分。

### 2.3 多场景推荐权重控制

难点：
- 学习搭子、社团搭子、兴趣同频的目标不同。
- 同一套排序结果无法充分表达不同场景偏好。

解决：
- 引入 `scenarioMode`。
- 在重排和展示层区分不同场景目标。
- 使用场景参数矩阵为后续实验保留入口。

### 2.4 工程验证与论文表述边界

难点：
- 开题报告包含量化目标，但当前缺少真实问卷和人工标注。
- 若直接写成正式实验结论，论文风险较高。

解决：
- 在 `../04_test/opening_report_validation_map.md` 中逐项标注证据和缺口。
- 在第 6 章明确模拟校园用户数据和代理相关性规则。
- 将真实用户研究写为后续工作。

## 3. 答辩可用精简说法

可以这样概括项目亮点：

> 本系统不是只做标签重叠，而是围绕校园用户匹配构建了“画像、召回、排序、重排、解释、反馈”的完整闭环。系统通过改进 TF-IDF 生成用户画像，通过校园场景规则和可信连接分调整排序，并把推荐解释绑定到标签贡献和规则命中证据上。为了答辩展示，系统还提供透明链路页面，可以看到从输入标签到最终解释的全过程。LLM 只用于解释润色，并保留规则回退，保证推荐结果可控。

## 4. 不建议使用的过度表述

不要写：
- 系统已经完成真实用户满意度验证。
- 推荐准确率已在真实线上环境达到工业级水平。
- LLM 参与推荐排序并提升准确率。
- 轻量探索机制已通过大规模实验证明最优。
- 所有开题报告量化目标均已正式达成。

建议写：
- 系统已完成工程实现和代理验证。
- 当前结果基于模拟校园用户数据和代理相关性规则。
- 系统具备后续接入人工标注、问卷验证和更大规模实验的基础。
