# 第 4 章 校园社交匹配推荐系统概要设计

本章在第 3 章需求分析的基础上，对校园社交匹配推荐系统进行概要设计。概要设计主要说明系统架构、功能结构、数据库设计和 Redis 设计，使后续详细设计与实现能够围绕稳定的模块边界展开。

## 4.1 系统架构设计

系统采用 Spring Boot 单体分层架构，整体结构如图 4-1 所示。校园用户和系统管理员通过前端页面或接口访问系统，系统内部按照接口层、应用服务层、领域能力层和数据访问层组织。接口层负责接收请求和返回统一响应；应用服务层负责编排用户、标签、画像、推荐、解释和反馈等业务流程；领域能力层负责画像权重计算、候选召回、相似度排序、校园规则重排、可信连接分和解释证据抽取；数据访问层负责 MySQL、Redis 以及查询仓储的访问。外部大语言模型服务只用于解释文本润色，推荐计算仍由系统内部确定性链路完成。

> 图 4-1 系统架构图

如图 4-1 所示，MySQL 用于保存用户、标签、画像、推荐结果、推荐解释和用户反馈等结构化数据；Redis 用于保存标签倒排索引、画像缓存和推荐缓存。该架构使推荐主链路集中在服务层和领域能力层，避免算法逻辑散落在控制器或数据访问代码中。

表 4-1 系统分层结构说明

| 层次 | 职责 | 典型组件 |
| --- | --- | --- |
| 接口层 | 接收页面或接口请求，完成参数校验和响应封装 | Controller |
| 应用服务层 | 编排用户、标签、画像、推荐、解释和反馈流程 | Service、ServiceImpl |
| 领域能力层 | 实现画像计算、召回、排序、重排、解释等核心策略 | Strategy、Model |
| 数据访问层 | 访问 MySQL、Redis 和查询仓储 | Mapper、Repository |

## 4.2 系统功能结构

根据第 3 章需求分析，系统功能结构如图 4-2 所示。系统以校园用户匹配推荐为核心，将功能划分为用户与标签维护、用户画像构建、匹配推荐生成、推荐解释、用户反馈更新和运行评估六个部分。其中，画像构建、匹配推荐生成、推荐解释和反馈更新是本文重点完成的功能。

> 图 4-2 系统功能结构图

用户与标签维护模块为推荐链路提供基础输入；用户画像构建模块将标签关系转化为权重向量；匹配推荐生成模块完成候选召回、相似度排序和校园规则重排；推荐解释模块生成可追溯解释；用户反馈更新模块记录反馈并触发画像更新；运行评估模块用于支撑系统测试和结果分析。

表 4-2 核心模块职责表

| 模块 | 主要职责 |
| --- | --- |
| 用户与标签维护 | 管理用户基础信息、标签定义和用户标签关系 |
| 用户画像构建 | 根据标签关系生成用户画像和 Top-K 核心标签 |
| 匹配推荐生成 | 完成候选召回、基础排序、校园规则重排和结果保存 |
| 推荐解释 | 根据标签贡献、规则命中和可信连接原因生成推荐解释 |
| 用户反馈更新 | 记录关注或忽略反馈，并根据反馈更新画像 |
| 运行评估 | 提供功能测试、透明链路、双视图对比和离线评估材料 |

## 4.3 数据库设计

系统数据库围绕推荐主链路设计，核心实体关系如图 4-3 所示。用户与标签通过用户标签关系建立多对多关系；用户画像保存标签权重向量和 Top-K 核心标签；推荐结果记录一次推荐任务中的候选对象、排序分数、名次和追踪标识；推荐解释保存解释文本和证据数据；用户反馈记录用户对推荐结果的关注或忽略行为。

> 图 4-3 系统 ER 图

如图 4-3 所示，用户表是推荐请求和候选对象的基础实体，标签表和用户标签关系表为画像计算提供输入。画像表保存聚合后的中间结果，便于推荐链路重复读取。推荐结果表与推荐解释表保持一对一或一对多的关联，使每条推荐结果都能回溯到解释证据。用户反馈表与推荐结果表关联，用于记录用户行为并支撑画像更新。

表 4-3 核心数据表说明

| 表名 | 用途 |
| --- | --- |
| `user` | 保存用户基础信息 |
| `tag` | 保存标签定义和标签类型 |
| `user_tag_relation` | 保存用户与标签关系，是画像计算的数据来源 |
| `user_profile` | 保存用户画像 JSON、Top-K 标签 JSON 和画像版本 |
| `recommendation_result` | 保存推荐对象、排序分数、名次和 trace 信息 |
| `recommendation_explanation` | 保存推荐解释、证据 JSON 和贡献 JSON |
| `user_feedback` | 保存用户对推荐结果的反馈行为 |

## 4.4 Redis 设计

Redis 主要用于支撑候选召回和画像缓存。标签倒排索引以标签 ID 为 key，value 为拥有该标签的用户集合。推荐时，系统根据目标用户画像中的 Top-K 标签读取多个倒排集合并合并候选用户，减少对全量用户逐一计算相似度的开销。

系统典型缓存数据包括标签倒排集合、用户画像缓存和推荐结果缓存。MySQL 仍是系统主数据来源，Redis 承担读取加速和索引缓存职责。当缓存缺失或索引需要重建时，系统可根据 MySQL 中的用户标签关系重新生成画像和倒排索引。

表 4-4 Redis 数据设计说明

| 数据类型 | Key 形式 | 用途 |
| --- | --- | --- |
| 标签倒排集合 | `recall:inv:tag:{tagId}` | 根据核心标签召回候选用户 |
| 用户画像缓存 | `profile:cache:user:{userId}` | 缓存画像权重向量和 Top-K 标签 |
| 推荐结果缓存 | `recommendation:detail:{userId}` | 缓存推荐详情，减少重复查询 |

## 4.5 本章小结

本章完成了系统概要设计。系统采用 Spring Boot 单体分层架构，以校园用户匹配推荐为核心进行功能划分，通过 MySQL 保存结构化业务数据，通过 Redis 支撑倒排召回和画像缓存，并围绕用户、标签、画像、推荐结果、推荐解释和用户反馈设计核心数据表。上述设计为第 5 章详细设计与实现提供了总体依据。
