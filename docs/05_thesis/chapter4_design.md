# 第 4 章 校园社交匹配推荐系统概要设计

本章在第 3 章需求分析的基础上，对校园社交匹配推荐系统进行概要设计。概要设计重点说明系统总体架构、模块划分、数据存储和接口组织方式，为后续详细设计与实现提供基础。系统采用 Spring Boot 单体分层架构，不引入分布式推荐平台或深度学习训练架构，以保证工程实现可控、模块边界清晰、测试验证可重复。

## 4.1 总体架构设计

系统采用单体分层架构，整体分为接口层、应用服务层、领域能力层和数据访问层。接口层负责接收前端或演示页面发起的 HTTP 请求，并返回统一响应；应用服务层负责编排业务流程，尤其是推荐主链路；领域能力层沉淀画像计算、排序、重排、解释等核心策略；数据访问层负责 MySQL、Redis 以及相关查询仓储的访问。

表 4-1 系统分层结构说明

| 层次 | 职责 | 典型组件 |
| --- | --- | --- |
| 接口层 | 接收 HTTP 请求，处理入参与响应 | Controller |
| 应用服务层 | 编排业务流程和推荐主链路 | Service / ServiceImpl |
| 领域能力层 | 实现画像、排序、重排、解释等核心策略 | Strategy / Model |
| 数据访问层 | 访问 MySQL、Redis 和查询仓储 | Mapper / Repository |

系统总体架构如图 4-1 所示。MySQL 用于保存用户、标签、画像、推荐结果、推荐解释和用户反馈等结构化数据；Redis 用于保存标签倒排索引、画像缓存和推荐缓存，以降低推荐链路中的重复读取成本。该结构使核心业务逻辑集中在 service 和 strategy 层，既便于测试，也便于在论文中解释系统运行过程。

## 4.2 模块划分

根据推荐链路和业务职责，系统划分为用户、标签、画像、召回、排序、重排、解释、反馈和推荐编排九个主要模块。模块划分围绕推荐流程中的职责边界进行组织，而非简单按照数据库表拆分。

表 4-2 核心模块职责表

| 模块 | 主要职责 |
| --- | --- |
| 用户模块 | 管理用户基础信息，向推荐链路提供用户上下文 |
| 标签模块 | 管理标签定义、标签分类和用户标签关系 |
| 画像模块 | 生成并维护用户画像 |
| 召回模块 | 根据用户画像生成候选用户集合 |
| 排序模块 | 对候选用户进行基础排序 |
| 重排模块 | 根据校园场景对排序结果进行调整 |
| 解释模块 | 生成可追溯的推荐解释 |
| 反馈模块 | 记录用户反馈，并触发画像轻量更新 |
| 推荐编排模块 | 串联画像、召回、排序、重排、解释和落库流程 |

其中，推荐编排模块是主流程入口，但不直接承担所有算法细节。画像、召回、排序、重排和解释分别由独立服务或策略组件完成，使每个阶段都能单独测试和替换。这样的划分可以避免算法逻辑散落在 controller 或 mapper 中，也能降低后续扩展不同场景策略的成本。具体推荐算法与核心机制将在第 5 章展开。

## 4.3 推荐主流程概要

系统推荐过程从用户标签开始，经过画像构建、候选召回、基础排序、场景重排和解释生成，最终返回 Top-K 推荐结果。用户反馈被记录后，会对画像进行轻量更新，并影响后续推荐。第 5 章将进一步展开各阶段的算法与核心机制。

> 图 4-2 推荐主流程概要图

从概要设计角度看，该流程明确了系统的数据流和控制流：用户标签关系是画像计算的起点，画像结果驱动召回和排序，排序与规则命中生成推荐结果和解释，用户反馈再回到画像更新环节。各阶段的权重计算、分数合成和解释约束将在第 5 章说明。

## 4.4 数据库设计

系统数据库围绕推荐主链路设计，核心表包括 `user`、`tag`、`user_tag_relation`、`user_profile`、`recommendation_result`、`recommendation_explanation` 和 `user_feedback`。这些表覆盖了用户基础信息、标签关系、画像结果、推荐明细、解释证据和反馈记录。

表 4-3 核心数据表说明

| 表名 | 用途 |
| --- | --- |
| `user` | 保存用户基础信息 |
| `tag` | 保存标签定义和标签类型 |
| `user_tag_relation` | 保存用户与标签关系，是画像计算的数据来源 |
| `user_profile` | 保存用户画像 JSON 和 Top-K 标签 JSON |
| `recommendation_result` | 保存推荐结果、分数、排序和 trace 信息 |
| `recommendation_explanation` | 保存推荐解释、证据 JSON 和贡献 JSON |
| `user_feedback` | 保存用户对推荐结果的反馈 |

数据库核心实体关系如图 4-3 所示。用户与标签通过 `user_tag_relation` 建立多对多关系；`user_profile` 保存聚合后的画像结果；`recommendation_result` 记录一次推荐任务中的候选对象、排序分数和追踪标识；`recommendation_explanation` 保存推荐解释及证据；`user_feedback` 记录用户对推荐结果的关注或忽略行为。

> 图 4-3 数据库 ER 图

将 `user_profile` 单独建表，是因为画像是聚合后的中间产物，推荐链路会反复读取。将 `recommendation_result` 与 `recommendation_explanation` 分表保存，是为了让推荐结果和解释证据保持清晰对应，也便于在测试与论文中展示推荐结果如何被解释。

## 4.5 Redis 设计

Redis 主要用于支撑候选召回和画像缓存。标签倒排索引以标签 ID 为 key，value 为拥有该标签的用户集合。推荐时，系统根据目标用户 Top-K 标签读取多个倒排集合并合并，避免对全体用户进行全量扫描。

典型 key 包括标签倒排集合 `recall:inv:tag:{tagId}` 和用户画像缓存 `profile:cache:user:{userId}`。

Redis 不是系统的唯一数据来源。MySQL 保存结构化主数据，Redis 承担加速读取和演示环境下快速重建索引的职责。当缓存缺失或需要重建时，系统仍可根据 MySQL 中的用户标签关系重新构建倒排索引和画像缓存。

## 4.6 接口组织设计

系统接口围绕推荐主链路组织，而不是按页面堆叠。用户与标签接口提供基础数据维护能力；画像接口负责构建或查询用户画像；推荐接口负责输出 Top-K 推荐结果及其排序、重排、解释证据；反馈接口负责记录用户行为；演示与评估接口用于支撑答辩展示和离线评估。

表 4-4 主要接口设计表

| 接口类别 | 设计目的 |
| --- | --- |
| 用户与标签 | 创建用户、查询用户、维护用户标签关系 |
| 画像 | 构建、重建或查询用户画像 |
| 推荐 | 获取 Top-K 推荐结果和推荐详情 |
| 解释 | 查询单条推荐解释及证据 |
| 反馈 | 提交关注或忽略反馈，触发画像更新 |
| 演示与评估 | 初始化校园用户数据集、展示故事线、导出评估结果 |

推荐接口除返回最终排序结果外，还应返回 `matchedTags`、`matchedRules`、`trustReasons`、`interestScore`、`campusScore` 和 `trustScore` 等字段。这些字段用于支持前端展示推荐依据和排序依据，并为测试章节提供可验证证据。

## 4.7 本章小结

本章完成了系统概要设计。系统采用 Spring Boot 单体分层架构，以推荐主流程为核心进行模块划分，通过 MySQL 保存结构化业务数据，通过 Redis 支撑倒排召回和画像缓存，并围绕用户、标签、画像、推荐、解释和反馈设计核心数据表与接口类别。该概要设计为第 5 章系统详细设计与实现提供了基础。
