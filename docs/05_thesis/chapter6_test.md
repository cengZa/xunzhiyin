# 第 6 章 系统测试

本章对校园社交匹配与可解释推荐系统进行测试。测试目标不是证明系统已经达到真实线上推荐产品效果，而是验证系统功能链路是否完整、核心模块是否符合需求、推荐解释是否能够回溯到计算证据，以及测试与演示材料是否能够重复执行。由于当前数据主要来自模拟校园用户数据，离线评估采用代理相关性规则，因此本章将相关结果表述为工程验证和代理验证。

## 6.1 测试目标

结合第 3 章需求分析和第 5 章详细设计，系统测试重点覆盖以下目标：

1. 验证用户、标签、画像、推荐、解释和反馈等基础功能是否可用。
2. 验证“画像 -> 召回 -> 排序 -> 重排 -> 解释 -> 反馈”推荐主链路是否能够闭环运行。
3. 验证推荐解释是否来自标签贡献、规则命中和可信连接原因，而不是脱离推荐过程单独生成。
4. 验证自动化测试、治理检查和离线评估材料是否可以重复执行。
5. 明确模拟校园用户数据和代理指标的适用边界，避免将代理验证写成真实用户实验结论。

## 6.2 测试环境

系统后端基于 Java 21、Spring Boot、MyBatis Plus、MySQL 和 Redis 实现，使用 Maven 进行构建和测试。测试环境分为自动化测试环境和本地联调环境，如表 6-1 所示。

表 6-1 测试环境说明

| 环境项 | 配置或用途 | 说明 |
| --- | --- | --- |
| JDK | Java 21 | 用于后端编译、单元测试和集成测试 |
| 构建工具 | Maven | 执行项目构建和测试用例 |
| 自动化数据库 | H2 内存数据库 | 用于接口集成测试，避免依赖本地 MySQL |
| 本地数据库 | MySQL | 用于本地运行、演示和表结构验证 |
| 缓存组件 | Redis | 用于画像缓存和标签倒排索引 |

自动化集成测试使用 H2 内存数据库完成接口闭环验证。本地 MySQL 与 Redis 主要用于联调和演示，若本地依赖未启动，相关测试按环境条件跳过，不影响核心自动化测试结论。

测试与演示使用模拟校园用户数据集。该数据集包含用户基础信息、标签、用户标签关系、画像、推荐结果、推荐解释和反馈记录，可用于验证推荐主链路和答辩演示稳定性。

表 6-2 测试数据规模

| 数据项 | 数量 |
| --- | --- |
| 用户数 | 18 |
| 标签数 | 18 |
| 用户标签关系数 | 86 |

该数据集不属于真实线上用户数据。离线评估中的相关性判断采用代理规则：当共同标签数量不少于 2，或双方专业相同且共同标签数量不少于 1 时，认为该候选关系满足代理相关性条件。

因此，离线评估可以用于说明推荐链路可运行、结果可解释、不同策略可对比，但不能替代真实人工标注或用户问卷。

## 6.6 离线评估设计

离线评估用于比较不同推荐策略在模拟数据集上的输出差异。当前评估设置四类基线，如表 6-5 所示。

表 6-5 离线评估基线

| 基线 | 含义 |
| --- | --- |
| 标签重叠 | 按标签重合程度近似模拟基础推荐 |
| 余弦排序 | 按用户画像向量余弦相似度排序 |
| 完整链路（无可信分） | 使用画像、召回、排序和校园规则重排，不叠加可信连接分 |
| 完整链路（含可信分） | 在完整链路基础上加入可信连接分 |

评估指标包括 Precision@K、HitRate@K 和解释覆盖率。其中 Precision@K 表示推荐列表中满足代理相关性规则的比例，HitRate@K 表示推荐列表中是否至少包含一个相关候选，解释覆盖率表示推荐结果是否包含解释文本或解释证据。由于相关性规则不是人工标注结果，这些指标仅用于代理验证。

## 6.7 离线评估结果

在 `interest_partner` 场景、`topK=3` 条件下，系统基于 18 个活跃用户、18 个标签和 86 条用户标签关系进行评估。评估结果如表 6-6 所示。

表 6-6 离线评估结果

| 基线 | 平均召回候选数 | 平均返回数 | Precision@K | HitRate@K | 解释覆盖率 |
| --- | --- | --- | --- | --- | --- |
| 标签重叠 | 9.6667 | 3.0000 | 1.0000 | 1.0000 | 1.0000 |
| 余弦排序 | 9.6667 | 3.0000 | 1.0000 | 1.0000 | 1.0000 |
| 完整链路（无可信分） | 9.6667 | 3.0000 | 1.0000 | 1.0000 | 1.0000 |
| 完整链路（含可信分） | 9.6667 | 3.0000 | 1.0000 | 1.0000 | 1.0000 |

在当前代理规则下，四类基线均取得较高指标。这说明模拟数据集中的标签、专业和兴趣关系能够支撑推荐链路输出稳定结果，也说明解释生成覆盖了评估结果中的推荐项。但需要注意，表 6-6 不能被解释为真实用户满意度达到 100%，其含义仅限于代理规则下的链路验证。

参数实验结果显示，当 TopK 从 3 增加到 5 时，Precision@K 出现下降，HitRate@K 和解释覆盖率保持为 1.0000，如表 6-7 所示。

表 6-7 TopK 参数实验结果

| TopK | Precision@K | HitRate@K | 解释覆盖率 |
| --- | --- | --- | --- |
| 3 | 0.9444 | 1.0000 | 1.0000 |
| 5 | 0.7333 | 1.0000 | 1.0000 |

该结果符合推荐列表扩展后的常见现象：返回数量增加后，弱相关候选更容易进入列表，Precision@K 会下降；只要列表中仍包含至少一个相关候选，HitRate@K 可以保持较高水平。

## 6.8 测试结果分析

综合功能测试、自动化测试、治理检查和离线评估结果，可以得到以下结论：

1. 系统主链路已经闭环。用户标签可以生成画像，画像可以驱动召回、排序、重排和解释，用户反馈可以回到画像更新环节。
2. 核心模块具备可测试性。画像、重排、解释、推荐编排等逻辑均有对应测试材料，接口集成测试能够验证主要业务流程。
3. 推荐解释具有可追溯性。解释文本基于标签贡献、规则命中和可信连接原因生成，LLM 仅用于可选改写，不改变推荐计算结果。
4. 演示材料具备可复现性。模拟数据、透明链路、双视图对比和离线评估导出可以支撑答辩展示。
5. 实验结论存在边界。当前评估依赖模拟校园用户数据和代理相关性规则，不能替代真实用户问卷、人工标注或线上长期反馈实验。

因此，本章测试结果能够支撑工程型毕业设计中的“系统实现完整、功能可运行、推荐链路可解释、测试材料可重复”结论；涉及真实用户满意度、真实 Top-K 满意比例和多轮反馈收益的结论应作为后续工作处理。

## 6.9 本章小结

本章从测试目标、测试环境、测试数据、功能测试、自动化测试和离线代理评估等方面对系统进行了验证。测试结果表明，系统已经实现校园社交匹配推荐的主要功能，推荐主链路能够稳定运行，解释与反馈机制具备工程可验证性。当前不足在于测试数据规模较小，离线评估依赖代理相关性规则，尚未补充真实用户问卷和人工标注实验。后续可进一步增加人工标注样本、真实问卷和响应时间统计，以增强实验结论的外部可信度。
