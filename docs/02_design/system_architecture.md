# System Architecture
# 系统总体架构设计

## 1. 设计目标

本系统面向校园社交匹配场景，采用结构化推荐架构，将推荐流程拆分为多个相互独立但逻辑衔接的模块，以保证：
1. 工程可实现
2. 推荐链路可解释
3. 各模块便于单独测试与优化
4. 论文表达与代码实现可保持一致

## 2. 总体架构风格

采用 Spring Boot 单体分层架构，核心由四层组成：

1. 接口层（Controller）
2. 应用服务层（Application / Service）
3. 领域能力层（Domain / Strategy）
4. 数据访问层（Mapper / Repository）

底层存储使用：
- MySQL：结构化业务数据
- Redis：倒排索引、缓存型画像、推荐结果缓存

## 3. 模块划分

### 3.1 用户模块（user）
职责：
- 用户基础信息管理
- 查询目标用户基础属性
- 提供推荐链路中的用户上下文

### 3.2 标签模块（tag）
职责：
- 标签定义与分类
- 用户标签关系维护
- 向画像模块提供原始标签数据

### 3.3 画像模块（profile）
职责：
- 基于改进 TF-IDF 构建用户兴趣向量
- 引入时间衰减
- 生成用户 Top-K 标签画像

### 3.4 召回模块（recall）
职责：
- 基于标签-用户倒排索引快速召回候选用户
- 降低排序计算规模

### 3.5 排序模块（ranking）
职责：
- 基于余弦相似度计算目标用户与候选用户之间的相似度
- 输出基础排序分数
- 记录标签贡献项

### 3.6 重排模块（rerank）
职责：
- 引入校园场景规则对基础排序结果进行再排序
- 控制年级差、专业相关性、社团重合度等业务约束

### 3.7 解释模块（explain）
职责：
- 从排序与重排过程提取可解释证据项
- 生成与推荐逻辑一致的解释文本

### 3.8 反馈模块（feedback）
职责：
- 记录用户对推荐对象的反馈
- 对兴趣画像进行轻量级更新

### 3.9 推荐编排模块（recommendation）
职责：
- 负责整个推荐主链路调度
- 串联画像、召回、排序、重排、解释、落库等流程

## 4. 主链路时序

1. 用户发起推荐请求
2. RecommendationService 获取目标用户画像
3. RecallService 根据画像 Top-K 标签从 Redis 倒排索引召回候选用户
4. RankingService 计算目标用户与候选用户的余弦相似度
5. RerankService 根据校园规则对结果做重排
6. ExplanationService 生成每个候选结果的解释文本
7. RecommendationService 保存结果并返回 Top-K 推荐列表

## 5. 反馈链路时序

1. 用户对推荐对象执行“关注”或“忽略”
2. FeedbackService 记录反馈
3. ProfileService 对相关标签权重做轻量调整
4. 更新后的画像进入下一轮推荐

## 6. 设计原则

1. 单体优先，不拆微服务
2. 模块职责清晰，避免算法逻辑散落各层
3. 解释必须来自排序与重排证据，不允许单独生成无依据解释
4. 优先保证 MVP 主链路可跑通
5. 为测试章节预留指标采集点
